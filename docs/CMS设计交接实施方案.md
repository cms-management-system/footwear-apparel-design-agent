# 鞋服设计智能体与 CMS 交接方案

依据：2026-10-08 录音自动转写稿（未校对，重点约 04:31–06:10、07:25–11:56、14:40–15:12）及 [鞋服 CMS 流程图](https://leo-ai-pm.github.io/apparel-cms/?v=20260922-05#overview)。录音中的岗位称呼和个别词句存在识别错误，以下仅将清楚、重复出现的流程意图作为需求；具体岗位与企业规则仍待实际团队确认。

## 一句话目标

产品负责人批准的 **具体需求包版本** 进入设计负责人待接收队列；负责人确认能否设计并分派给设计人员；设计人员借助智能体生成、比较和修订方案；设计负责人审核后把关联原需求版本的响应回传 CMS。任何人不能把未批准需求或单条穿搭意向直接当成设计任务。

## 已有能力与缺口

| 环节 | 当前事实 | 下一步 |
|---|---|---|
| CMS 需求包 | 共享 CMS 仓库已有仅设计 Agent 可读取的 `GET /api/packages?status=approved` 和按 ID 读取接口，未批准包不可读 | 设计端用服务端专用 Key 接入，列表分页、去重与版本校验 |
| 产品需求工作台 | 当前界面的“批准需求”写入本机 `workbench-cases.sqlite`；真正回传 CMS 的 `POST /drafts/{id}/publish` 是另一条流程 | 将负责人批准的最终版本形成证据包、回传 CMS，并显示 CMS 已接收/已批准状态；失败不可显示“已交设计” |
| 优先级 | 产品端本机要求 P0–P3 与依据；共享 CMS 主分支的需求包契约尚未包含该字段 | 先合并优先级迁移与审核规则，再用于设计任务排序；不得只靠前端颜色表示优先级 |
| 鞋服设计 Agent | 已支持对话澄清、要求单、风格方向、出图、版本修订、确认与打样资料；此前无 CMS 读取连接器 | 本次加入服务端只读连接器；后续建立负责人收件箱、分派和回传 |
| 设计回应 | CMS 已有 `POST /api/design-responses` 和负责人审核入档 | 设计负责人确认选中版本后上传响应，带 `package_id`、`design_version_id`、版本、可公开访问的图片 URL；失败可重试且不能重复建档 |

## 设计负责人工作台

1. **待接收**：卡片显示需求名称、`package_id`/版本、优先级及依据、来源信号数、硬约束、证据缺口；点击展开已批准的原始需求包。仅看到 CMS 已批准版本。
2. **可行性判断**：负责人选择“接收”“退回澄清”“暂缓”并写原因。智能体可检查约束冲突、资料缺口和现有款式，但结论由负责人确认。
3. **分派**：按鞋、上装、裤装等专长和当前负荷推荐设计人员；负责人可拖动卡片或选择姓名调整。自动分派只能作为建议，保留人工确认和改派记录。
4. **审核回传**：查看设计人员提交的候选图、版本差异、需求逐项响应与未解决约束；选择通过、退回修改或无法满足。通过后回传 CMS，显示回传结果和追溯链接。

## 设计人员工作台

只显示分派给自己的任务，按“待澄清 → 要求单待确认 → 设计中 → 待负责人审核 → 已回传/退回”组织。每张任务卡进入现有设计项目，预填来源需求和约束，但不自动确认要求单或触发付费出图。设计人员可以与智能体对话，要求它查找材料/商品资料、列出约束冲突、规划方向、生成与比较候选，并看到每步依据和成本；人确认要求单、生成动作与最终提交。

## 交接契约与状态

`package_id + version` 是不可变的来源标识。设计端保存 CMS 原包快照、接收时间、负责人、经办人和本地项目 ID；同一版本重复拉取不创建新任务。返工产生新版本并关联旧版本，不覆盖已批准历史。所有跨阶段动作记录操作者、时间与原因。

最小链路：`CMS approved → 设计负责人待接收 → 已接收/待澄清 → 已分派 → 设计草稿 → 负责人审核 → CMS design_response draft → CMS 人工入档`。产品开发、打样和生产是后续阶段，设计响应本身不等于批准打样。

## 实施顺序与验收

1. **数据链**：产品负责人审批后真实回传 CMS；设计专用 Key 能拉到已批准包，未批准包、错误 Key 均被拒绝。连接器已建立只读入口，但未连接到设计 UI。
2. **组织链**：新增设计负责人/设计人员账号、服务端权限与收件箱；设计负责人接收、退回、分派，设计人员只见本人任务。录音提出的“一键角色切换”仅用于演示，正式权限以登录账号为准。
3. **设计链**：把批准需求映射为设计要求草稿，人工确认后调用现有设计能力；设计负责人审核版本并回传 CMS，图片使用可访问的稳定 URL。
4. **端到端验收**：用一条非演示信号，从穿搭上传、产品归因审批、设计负责人分派、设计人员修订、设计回应回传到 CMS 追溯完整走通；同时测试退回重审、重复拉取、断网重试、权限越权与版本冲突。

本文件描述待实现目标；不能把流程图、录音或现有演示数据当作真实企业需求已验证的证据。
